## Runtime integration

The incident agent uses the translated result/output contract for provider-visible tool responses. Configure the approximate body budget with:

```toml
[harness]
tool_output_tokens = 10000
```

The supported range is 64–32768 approximate tokens, at four UTF-8 bytes per token. This is an output byte budget, not a tokenizer measurement. Truncation retains the beginning and end and inserts an explicit omission marker outside the retained-body budget. Stored evidence retains its existing independent 16 KiB per-item bound. Initial investigation context and aggregate model requests retain their separate context limits. The `tool_output_bounded` trace event records provider-response truncation.

The toolbox and run harness validate public arguments before dispatch. The supported schema subset includes object fields, required/additional properties, type unions, enum/const, local references, oneOf/anyOf/allOf, array items/uniqueness, lengths, and inclusive numeric ranges. Validation is limited to depth 32 and 8,192 visited nodes. Unrecognized keywords, including pattern/format and remote references, are not implemented (remote references fail explicitly). This is not a complete JSON Schema engine. Connector-specific checks still run.

For embedded callers, `Toolbox::runtime_catalog(service)` adapts the actual configured toolbox into the async `RuntimeTool` interface. Call `prepare().await` first for MCP discovery. Capture one immutable catalog snapshot per request. The adapter collects service-scoped evidence; incident IDs, run budgets, checkpoints, and report validation remain the responsibility of the incident engine. The embedding executor does not grant approval for external actions.

`execute_tool_calls` validates the entire role/ID batch before dispatch. A turn-ending tool can share a batch only with bookkeeping tools, which run first; results retain provider order. Host cancellation and terminating results leave explicit skipped outcomes. Before-hook errors block dispatch; after-hook errors retain the prior result. Callback failures represented by Rust `Result` are handled; arbitrary panics in tools/hooks are programming errors and are not isolated. Configured arguments are scoped by tool name and protected keys cannot be supplied by the model. Partial-update observer panics are isolated.

## Validation and remaining work

`tests/fixtures/tool-port.json` contains 233 outputs generated by executing selected functions from the audited source revision against deterministic inputs: 180 UTF-8 truncation cases, six multipart cases, 40 role combinations, and seven budget cases. The Rust tests compare these outputs exactly. Additional tests exercise snapshot replacement, schema errors, hook rejection, cancellation, argument isolation, real toolbox dispatch, and the production agent's provider-output/persistence boundary.

Deliberate changes include recursive input validation and exclusive oneOf matching, capped catalog/batch sizes, duplicate-ID rejection, saturating arithmetic, value-free errors, asynchronous callbacks, and per-instance budgets. These changes are tested separately and are not described as exact equivalence.

Remaining shared-tool work includes dynamic function-schema inference equivalents, richer evidence/retrieval metadata, full approval metadata, all source telemetry adapters, compatibility entry points, and complete source test migration. The rest of the 2,208-module application remains subject to the [coverage inventory](coverage.md).
